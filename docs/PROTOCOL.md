# Pairing and local transport

1. Both phones advertise and scan over BLE. On first contact the pairing channel exchanges commitments before revealing identity material and fresh nonces. Each side checks the peer signature and the displayed verification code. Room stores the peer's device ID and identity-key fingerprint. Names are editable labels.
2. Both confirmations cover the exchange transcript. The initiator sends a fresh session token. Local endpoint hints let the phones reconnect when multicast discovery fails. Trusted identity checks also apply when negotiating temporary direct-network credentials.
3. The identity certifies separate TLS signing credentials. Peers verify the binding to the pinned identity, device ID and validity period before trusting a connection. The Netty listener and Wi-Fi clients authenticate the session before carrying application traffic. Forgetting a peer revokes its local trust.
4. A versioned WebSocket carries chat and transfer control. Each message has an ID. The sender keeps it pending until the receiver persists it and returns a receipt. File offers carry metadata and the expected SHA-256. Acceptance grants access to ranged downloads. The receiver writes verified blocks, persists a durable offset and checks the complete SHA-256 before publishing the file and acknowledging it.
5. A direct link uses the same trust checks. Both phones can fall back to the LAN path, including a hotspot. Benchmark-only TCP uses generated bytes and an authorization proof conveyed over pinned TLS. The raw benchmark is compiled only into debug builds.
